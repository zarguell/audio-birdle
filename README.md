**Audio Birdle** is a daily audio-based bird guessing game inspired by Wordle — but with birds. Listen to the mystery bird call and identify the species. It is a static, client-side web app generated by **Python + Jinja** and deployed on **Cloudflare Workers**, with a small Worker for the optional Discord integration (only `/api/*` invokes it).

**Audio Birdle is live** on the web and as a Discord Activity. Play at
[audio-birdle.sechostlab.com](https://audio-birdle.sechostlab.com), or add the
bot to a Discord server below.

I created this game after being inspired by Mitch's [Birdle](https://github.com/mitchbeebe/new-birdle). As a birder, I wanted to practise sound identification, so I built an audio-first daily challenge.

---

## Features

- **Daily challenge:** a new bird every day, selected from recent eBird observations.
- **Normal mode:** four choices, four guesses.
- **Hard mode:** free-text search, six guesses, progressive taxonomic hints (order → family → genus).
- **Practice mode:** unlimited rounds with normal or hard mechanics; nothing is saved to stats.
- **Regional play:** US, US Lower 48, Ireland, Germany, Spain, Italy, Netherlands, Portugal, France, the United Kingdom, South Africa, Costa Rica, Mexico, Argentina, Thailand, Japan, New Zealand, Canada, and Australia, with a searchable region directory and pinned/recent regions. See the [region roadmap](docs/regions-roadmap.md).
- **Audio:** multiple recordings per bird where available.
- **Stats and archive:** streaks, win rate, regional breakdown, and a replayable history of past challenges.
- **Share results:** Wordle-style emoji result grid.
- **Offline-tolerant data:** the game falls back to deterministic hash selection when daily data is unavailable.
- **No account, no tracking:** progress lives in `localStorage`.
- **Discord Activity:** play the same game inside Discord, with a public board
  message, a **Play now!** button, and per-channel daily summaries.
- **Channel groups:** each channel gets its own streak and leaderboard, scoped
  by region and mode. Scores are never compared across regions.

## Play in Discord

Audio Birdle runs as a Discord Activity, with a bot that posts boards and daily
summaries in the channel.

1. [Add Audio-Birdle to a server](https://discord.com/oauth2/authorize?client_id=1575568221715697744&scope=bot%20applications.commands&permissions=54272)
   (Manage Server required). The same install link and walkthrough are on
   <https://audio-birdle.sechostlab.com/discord/>.
2. Open the **App Launcher** — desktop: the button at the right of the message
   bar; mobile: the button at the left — and choose **Audio-Birdle**. The entry
   point is not shown in `/` autocomplete.
3. Play the daily puzzle inside Discord. A public "`<name>` is playing" card is
   posted and edited with the result, and friends can launch from its
   **Play now!** button.
4. Run `/audiobirdle-setup` in a channel to receive that channel's daily
   summary.

| Command | What it does |
|---|---|
| `/audiobirdle-setup` | Post daily summaries in the current channel (Manage Server) |
| `/audiobirdle-stats` | Your record |
| `/audiobirdle-forget` | Delete your stored Discord data |

The bot appears **offline** by design: it uses HTTP interactions only, with no
Gateway connection. Privacy: <https://audio-birdle.sechostlab.com/privacy/> ·
Terms: <https://audio-birdle.sechostlab.com/terms/>.

## Stack

| Layer | Choice |
|---|---|
| Site generator | Python 3 + Jinja2 |
| Client | Vanilla ES modules, no bundler, no framework runtime |
| Styles | Hand-written, mobile-first CSS with a warm paper / pixel-nature theme |
| Data pipeline | Python scripts (pandas, requests, BeautifulSoup, Selenium) |
| Tests | pytest, Node's built-in test runner, Playwright |
| Hosting | Cloudflare Workers (static assets + a `/api/*` Worker) |

The old React/Vite client and its build chain have been removed. The only Node
packages in the repository are lint/test tooling; they are pinned in
`package-lock.json` and updated by Renovate.

Visual direction: warm paper panels laid over a pixel-art forest scene.
Parchment panels, wood-framed HUD controls, a vendored VT323 display font, and
original SVG scene art keep the theme lightweight and self-hosted.

## Architecture

```
sitegen/                  Python static site generator
├── build.py              Render pages, copy assets, write data manifest
├── data.py               Validate committed game data
├── data_manifest.py      SHA-256 manifest for cache-safe data loading
├── cli.py                `python -m sitegen build|manifest|serve`
├── templates/            Jinja pages, macros, and HTML templates
├── static/css/           Lintable CSS (tokens, layout, components, game)
├── static/fonts/         Vendored VT323 display font
├── static/img/           Original SVG scene art and bird mark
├── static/js/core/       Data loading, game state, hash, audio, share utils
├── static/js/ui/         DOM components (guesses, completion, autocomplete)
├── static/js/pages/      Small entry points per page
└── vendor/               Pinned Forever AI Components provenance

worker/                   Cloudflare Worker for the Discord integration
├── index.js              Routed only for /api/*
├── lib/                  Discord REST, Ed25519, streak helpers
└── migrations/           D1 schema (boards, results, launches, channels)

public/                   Committed static data, icons, and Cloudflare headers
├── data/*.json           Generated by the Python data pipeline
├── data/manifest.json    SHA-256 of every data file (regenerated daily)
├── favicon*              Browser favicon sizes
├── apple-touch-icon.png  iOS home-screen bookmark icon
├── site.webmanifest      Web app manifest
└── _headers              CSP and cache policy

scripts/                  eBird / Macaulay / Xeno-canto data pipeline
tests/                    Python unit/integration, JS unit, browser E2E
dist/                     Generated site output (gitignored)
```

### Pages

`/`, `/play/`, `/normal/`, `/hard/`, `/practice/`, `/stats/`, `/archive/`,
`/settings/`, `/privacy/`, `/terms/`, and a static `404.html`. Every page is
rendered by Jinja at build time; page scripts only load data and handle
interaction. There are no inline scripts, inline styles, or HTML strings in
Python.

### Cache consistency

Cloudflare and browser caches can otherwise serve an old bird shard next to a
new `daily.json`. The site handles this in three layers:

1. **Hashed static assets.** CSS/JS live under `/assets/<content-hash>/` and are
   served `immutable`.
2. **Hashed data requests.** `/data/manifest.json` lists the SHA-256 of every
   data file. The client fetches manifest with `no-store` and requests each file
   as `/data/file.json?v=<hash>`. A stale manifest or mixed cache is detected by
   hash comparison and retried with a cache-busting URL.
3. **Daily manifest regeneration.** The daily-update workflow regenerates
   `public/data/manifest.json` after the data scripts run, so a deploy always
   describes one coherent snapshot.

There is deliberately **no service worker**.

## Development

### Prerequisites

- Python 3.11+
- Node.js 24+ (lint and JS unit tests only)
- Chromium for Playwright (`python -m playwright install chromium`)

### Setup

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements-dev.txt
npm ci
python -m playwright install chromium
make hooks               # install pre-commit and pre-push hooks
```

### Commands

```bash
make serve              # Build and serve at http://127.0.0.1:8000
make build              # Render dist/ (installs Jinja into .build-deps)
make lint               # ESLint + Stylelint + djlint + pylint
make check              # lint + Python/JS tests + build (pre-push)
make hooks              # Install pre-commit and pre-push hooks
make test-python        # pytest, excluding browser/live tests
make test-js            # Node unit tests
make test-e2e           # Build + Playwright against a local server
make test-live          # Playwright against LIVE_SITE_URL
make check-all          # make check + browser tests
```

Commits run the linters through pre-commit. Pushes run `make check`.
Use `pre-commit run --all-files` for a full lint pass without committing.

Equivalent direct commands:

```bash
bash scripts/build-site.sh          # dependency-free build wrapper
python -m sitegen build            # when Jinja is already installed
python -m sitegen serve --port 8000
pytest tests/ -m "not e2e and not live" -v
node --test tests/js/*.test.js
pytest tests/e2e -m "not live" -v --no-cov
```

### Data pipeline

The daily GitHub Action at 05:00 UTC runs the Python scripts in `scripts/`,
regenerates `public/data/manifest.json`, tests the real data, and commits the
result. The data scripts still use the eBird API and the Macaulay/Xeno-canto
recordings; see [`scripts/README.md`](scripts/README.md).

## Deployment

The site is a Cloudflare Worker with static assets. HTML, `/assets/*`, and
`/data/*` are served by the assets binding; only `/api/*` invokes the Worker,
which powers the Discord Activity and bot. Static page views are not metered.

1. In the Cloudflare Workers Builds settings, set the build command to:

   ```bash
   bash scripts/build-site.sh
   ```

   `npm run build` invokes the same script if the existing integration uses it.

2. Keep the output directory as `dist`. `wrangler.jsonc` points assets at
   `./dist/`, uses `404-page` handling, and routes only `/api/*` through the
   Worker.
3. `public/_headers` is copied into `dist/` and controls CSP and cache policy.
4. For Discord, set `DISCORD_CLIENT_ID` in the Workers Builds **build**
   environment and the four Worker secrets, then follow
   [`docs/discord-production.md`](docs/discord-production.md) for the app,
   interactions endpoint, URL mappings, install, and command registration.
   Day-two operations are in [`docs/discord-runbook.md`](docs/discord-runbook.md).

### Self-hosting the Discord integration

1. Create a Discord app, add the OAuth2 redirect, enable Activities, and install
   it with `bot` + `applications.commands` (permissions `54272`).
2. Deploy this repository as a Worker (`wrangler.jsonc` has `main` and routes
   only `/api/*`), with the D1 database and migrations.
3. Set `DISCORD_PUBLIC_KEY`, `DISCORD_CLIENT_ID`, `DISCORD_CLIENT_SECRET`, and
   `DISCORD_BOT_TOKEN` on the Worker, plus `DISCORD_CLIENT_ID` in the build
   environment.
4. Set the interactions endpoint, Activity URL mapping `/`, and audio mappings
   `/xc` and `/cornell`.
5. Register the entry point and admin commands with
   `node scripts/register-discord-command.mjs`.

The full checklist — including the entry-point type-12 rule, the `guilds` OAuth
scope, the multi-page auth cache, and the audio mappings — is in
[`docs/discord-production.md`](docs/discord-production.md).

Cloudflare's build image includes Python, so no Node build step is required.

## Testing

- **Python:** data scripts, site generator, manifest hashing, template output.
- **JavaScript:** hash parity, taxonomy, answer options, practice logic, game
  state migration, share formatting.
- **Browser E2E:** local built site; normal/hard/practice flows, persistence,
  reset, archive, stats, cache headers, manifest consistency.
- **Worker:** Discord interaction signatures, board/session/result endpoints,
  per-channel summaries, rate limits, and retention.
- **Live integration:** scheduled workflow hits the deployed site and verifies
  assets, CSP, cache headers, data hashes, and that the normal game boots.
